# Code Agent Harness：阶段模型的预期指标与验收标准


## 1. 已知的单次代码生成结果（实测）

来源：原后训练项目 `READJPG.md` 的 HumanEval / HumanEval+ 评测记录。这里的 `pass@1` 是单次生成结果，不包含 Agent 修复。

| 阶段 | 模型含义 | HumanEval pass@1 | HumanEval+ pass@1 | 解释 |
|---|---|---:|---:|---|
| Base | Qwen2.5-7B 基座 | 0.880 | 0.810 | 作为后训练前的对照。 |
| SFT | 1,000 条代码指令数据微调 | 0.817 | 0.750 | 小规模数据和固定输出格式使泛化出现退化，不能假定 SFT 必然优于 base。 |

| Coder 对照 | 原项目记录的 `base-coder` | 0.909 | 0.848 | 更强代码模型的上界参考，不应与 7B 学生模型混作同一训练阶段。 |

## 2. Agent 评测口径

对同一批**未参与训练、也未用于构造轨迹数据**的代码任务，运行 `max_turns=3` 的生成—执行—修复流程。建议优先使用 HumanEval+ 或独立 MBPP 测试集，并对每个 checkpoint 使用完全相同的题目、提示词、verifier、温度、最大生成长度和超时设置。

| 指标 | 定义 |
|---|---|
| `pass@1` | 第一轮生成直接通过所有测试的比例；应接近但不必等于离线 HumanEval+，因为 prompt 和执行环境可能不同。 |
| `pass@3` / `repair_success_rate` | 最多 3 轮后通过所有测试的比例。 |
| `repair_gain` | `pass@3 - pass@1`，衡量执行反馈的绝对收益。 |
| `avg_turns` | 每题实际生成轮数；首轮通过的样本只计 1 轮。 |
| `timeout_rate` | 至少一次执行超时的任务比例。 |
| `syntax_error_rate` | 首轮因语法错误或解析失败导致执行失败的比例。 |

## 3. Agent 指标

下表用于决定“实验结果是否符合常识、是否需要排查 verifier/prompt/部署”。区间不是承诺值：真实模型在不同解码参数、测试集和反馈格式下可能明显偏离。

推导原则：

1. `pass@1` 以已知 HumanEval+ 的相对排序为锚点，并为 Harness prompt/部署差异保留约 ±2 个百分点波动；
2. 执行反馈只应修复一部分可局部定位的错误，因此预期 `repair_gain` 为 3–6 个百分点，而非不合理地大幅跃升；
3. SFT/DPO 的首轮效果不应被人为写成超过 base；GRPO/OPD 因训练中已经接触可执行或在线反馈，预期可修复性略好；
4. Coder 对照仅作参考，不拿它证明 7B 后训练收益。

| 阶段 | pass@1 | pass@3 | repair_gain | avg_turns | timeout_rate | 解释 |
|---|---:|---:|---:|---:|---:|---|
| Base | 0.79–0.83 | 0.84–0.88 | 0.03–0.06 | 1.25–1.40 | 0.02–0.05 | 基座首轮能力较稳，执行反馈可修复部分边界/实现错误。 |
| SFT | 0.73–0.77 | 0.78–0.83 | 0.03–0.06 | 1.30–1.45 | 0.03–0.06 | 与 HumanEval+ 0.750 对齐，格式约束可能增加解析稳定性，但不应掩盖任务泛化退化。 |
| SFT + DPO | 0.75–0.79 | 0.81–0.85 | 0.04–0.06 | 1.28–1.43 | 0.02–0.05 | 偏好训练应减少明显的低质量实现，但未必改善复杂算法错误。 |
| SFT + GRPO | 0.79–0.83 | 0.85–0.89 | 0.04–0.06 | 1.22–1.38 | 0.01–0.04 | 可执行奖励应降低可被测试暴露的错误，重点观察断言失败是否减少。 |
| SFT + OPD | 0.79–0.83 | 0.85–0.89 | 0.04–0.06 | 1.22–1.38 | 0.01–0.04 | 在线教师反馈可能改善首次方案与修复解释，但需要真实测试验证。 |
| Coder 对照 | 0.83–0.87 | 0.88–0.92 | 0.03–0.05 | 1.18–1.32 | 0.01–0.03 | 作为更强代码模型的运行时能力参照。 |

## 4. 预期结果的正确解读

### 合理情况

- `pass@3 > pass@1`，且 `repair_gain` 落在 3–6 个百分点：说明 verifier 反馈可修复一部分局部错误；
- GRPO/OPD 的 `timeout_rate`、格式失败或断言失败低于 SFT：可作为执行反馈训练带来行为改善的线索；
- 更强 Coder 对照的首轮能力更高，但其相对 repair gain 未必最大，因为可修复空间更小。

### 需要排查的情况

- `pass@3` 与 `pass@1` 完全相同：检查是否真的把 stderr/失败测试传入了下一轮 prompt；
- `repair_gain` 超过约 10 个百分点：检查测试是否泄漏进 prompt、不同轮是否使用了不同 verifier、或是否误把多样本采样当作修复收益；
- Harness 的 `pass@1` 与离线 HumanEval+ 相差超过约 5 个百分点：检查模型模板、最大长度、代码提取、采样参数和任务格式；
- SFT/DPO/GRPO/OPD 的真实排序与上表不同：保留真实排序，不应为符合预期而调整数据。

## 5. 真实实验完成后的替换规则

每次运行应保存：模型名称/commit、数据集版本和样本数、温度、最大 token、最大轮数、verifier 版本、`trajectories.jsonl` 与 `summary.json`。随后：

1. 将第 3 节的预期区间替换为真实点估计，并附任务数；
2. 报告 `pass@1`、`pass@3` 与 `repair_gain`，不要只报最终成功率；
3. 仅在真实数据稳定复现后，将指标压缩写入简历；
4. mock 的 `2/2` 修复成功只用于单元测试，永远不与模型实验混合。
